# Environment for YOUR kernels and the harness itself.
#
# torch and triton are deliberately NOT listed. The base venv is created with
# --system-site-packages so it inherits the CUDA-matched torch already present
# in the RunPod PyTorch image. Reinstalling torch here would mean guessing a
# CUDA wheel tag, downloading several GB, and risking a build that does not
# match the driver on the box.
#
# WHEN TO OVERRIDE THAT. RunPod's newest official PyTorch image is torch 2.8,
# while vLLM 0.27.1 and SGLang 0.5.18 both pin torch 2.13.0 (and Triton 3.7.1)
# into their own venvs. Inheriting means your kernel is compiled by one Triton
# and the baselines by another, which confounds the comparison you are trying to
# publish: a difference could be your schedule or could be the compiler.
#
# To pin base to the same torch the baselines use:
#
#   MOE_BASE_TORCH='torch==2.13.0' \
#   MOE_TORCH_INDEX='https://download.pytorch.org/whl/cu128' \
#     bash scripts/setup_runpod.sh base
#
# Check `nvidia-smi` first: a cu13 wheel needs driver r580+. Pick the wheel index
# that matches the driver, not the image name. The download is a few GB, once,
# onto the persistent volume.
#
# ON A LAPTOP the same omission has to be filled by hand, because
# tests/conftest.py and moe/bench/timing.py import torch at module level and
# nothing here installs it: after `uv pip install -e ".[dev]"`, add
#
#   uv pip install --python .venv/bin/python torch --index-url https://download.pytorch.org/whl/cpu
#
# README.md "Running it" is the documented path and tests/test_docs.py keeps
# the numbers on that page true. Without the CPU wheel pytest fails while
# loading conftest.py with zero tests collected and run_all.sh --dry-run exits
# 1, which is what a stranger got from this file's silence until 2026-09-03.

# THE CLOCK SAMPLER'S ONLY SOURCE. moe/bench/timing.py reads the SM clock under
# load through torch.cuda.clock_rate, which is torch's NVML binding, and it
# refuses to fork nvidia-smi inside a timed region (tens of milliseconds on the
# host thread that is enqueueing work is not a clock sample, it is a
# perturbation of the thing being measured). torch needs nvidia-ml-py for that
# call and does not depend on it. Without this line the pod's base venv has no
# NVML, every KernelTiming records clock_source "none", the LEVEL flag is None
# on every row, and the fix for "the ladders record no clock while the same
# session shows 62-97% throttling" is defeated silently. vLLM and SGLang each
# pull nvidia-ml-py transitively today; it is named in all three files so a
# release that drops the transitive dependency cannot take the clock with it.
nvidia-ml-py

# download, on metered pod time. 4.53.3 is the last release that still defines

# so the cap costs them nothing.
